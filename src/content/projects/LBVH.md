## Why should we care?

Bounding Volume Hierarchies (BVHs) are a crucial acceleration structure in ray tracing renderers. Without them, ray tracing would be unreliably slow because of ray-primitive intersection costs. BVHs address this by grouping primitives inside axis-aligned bounding boxes (AABBs), so large parts of the scene can be skipped during traversal.

Two factors determine how effective a BVH is: construction time and hierarchy quality. Better trees minimize traversal cost, but typically need expensive computations and slower construction, such as the surface area heuristic. For static scenes this may not matter, but for dynamic scenes and animations, where the hierarchy must be rebuilt frequently, slow construction becomes a significant limitation. Linear BVHs (LBVHs) are a potential solution: they use Morton codes to turn hierarchy construction into a parallelizable sorting problem (Figure 1), which allows much faster construction at the expense of slightly lower tree quality.

In this project, I implement a fully GPU-parallel LBVH build in OpenCL, based on the work of Lauterbach et al. and Karras:

1. **Can the whole build run in parallel on the GPU?** Morton codes, a radix sort, the hierarchy and the bounding boxes, all as GPU kernels, written from scratch.
2. **Is it faster than building on the CPU?** Compared against the same LBVH algorithm on the CPU and a naive spatial-median BVH, on models from 5 thousand to 28 million triangles.
3. **What does it cost in tree quality?** Measured as bounding-box and primitive intersection tests per ray.

*Note: this builds on Peter Shirley's Ray Tracing in One Weekend series, a basic C++ Monte Carlo path tracer. My contributions are the parallel LBVH pipeline in OpenCL, triangle primitives, and mesh loading with tinyobjloader.*

## The LBVH pipeline

Karras's LBVH build has four steps: compute Morton codes, sort them with a radix sort, build the hierarchy from the sorted codes, and walk the hierarchy to build each node's bounding box. Each step is a separate GPU kernel, except for the radix sort, which needs three (Figure 2).

### Morton codes

Following Lauterbach et al., I define a 2<sup>k</sup> × 2<sup>k</sup> × 2<sup>k</sup> lattice over the world-space AABB. Using the centroid of each primitive's bounding box, its coordinates are quantized into k-bit integers giving its lattice cell, and a 3k-bit Morton code is generated by interleaving the bits of x, y and z. I use k = 10, since the resulting 30-bit Morton codes align well with GPU cache behaviour. This phase parallelizes easily, with one GPU thread per primitive.

### Radix sort

Radix sort sorts multi-digit keys one digit at a time: each pass groups elements into buckets by the current digit and reorders the sequence accordingly, and repeating this for all digits gives a fully sorted sequence. I perform a least-significant-digit parallel radix sort based on Satish et al. Each pass processes a 4-bit digit of the Morton codes, giving 16 buckets; with 32-bit keys, that is 8 passes. Each pass has three phases:

- **Histogram.** Blocks of 256 threads, each thread handling 4 Morton codes, so a block covers 1,024 codes and there are `p = ⌈N / 1024⌉` blocks for `N` primitives. To avoid race conditions, each thread counts the current digit of its 4 codes in its own 16-bucket histogram. These are copied to global memory, laid out by digit, then by block, then by thread: 16 × p × 256 entries.
- **Global prefix sum.** A Blelloch scan over the whole histogram: each block loads two entries per thread into local memory, so 256 threads scan 512 entries. An up-sweep computes partial sums in place and writes each block's total to a separate array; the last element is set to zero and a down-sweep produces an exclusive prefix sum. A second scan over the block totals usually fits in a single block (for very large scenes it falls back to a sequential CPU scan), and adding each block's scanned total to the next block gives the final scanned histogram.
- **Scatter.** Each thread loads its part of the scanned histogram into local memory, and for each of its four primitives uses the digit to find the output position, writes the primitive there, and increments the histogram entry for subsequent writes.

### Hierarchy

To build the tree from the sorted primitives, I follow Karras's fully parallel algorithm. Unlike earlier approaches that need several passes, it assigns one thread to each internal node, so the whole hierarchy is built in a single kernel launch. First, N threads initialize the N leaves, stored at indices `[N − 1, 2N − 2]`; then N − 1 threads handle the N − 1 internal nodes at indices `[0, N − 2]` in parallel. The root is always node 0 and covers the whole sorted range.

For each internal node, we find the range of leaves it covers and the split point within that range, by binary searching for where the longest common prefix of the Morton codes changes. The common prefix length is `δ(i, j) = clz(m_i XOR m_j)`, with `clz` counting leading zeros; when two codes are equal, `32 + clz(i XOR j)` breaks the tie. Node `i` first picks a direction by comparing `δ(i, i + 1)` with `δ(i, i − 1)`, binary searches for the length of its range, and then finds its split `s`. Its children become nodes `s` and `s + 1` (as leaves or internal nodes), and their parent becomes `i`.

### Bounding boxes

With the tree in place, the bounding boxes are computed bottom-up, also as described by Karras (Figure 3). Each of the N threads starts at a leaf and walks up towards the root through the parent pointers. Every internal node has an atomic counter, initialized to zero. A thread that arrives first sees 0 and terminates; the second sees 1, which means both children have valid boxes, so it computes the parent's box as their union and continues upward. This way, each internal node's box is computed exactly once, with no race conditions.

## Results

I evaluate the GPU LBVH against the CPU LBVH and the naive spatial-median BVH on four models of increasing complexity: the Bunny (5K triangles), Armadillo (213K), Dragon (871K) and Lucy (28M). All tests ran on an AMD Radeon RX 9060 XT with OpenCL 1.2, rendering at 1280×720 with 100 samples per pixel, about 92 million rays per scene.

### Construction time

For small scenes, the GPU build has significant overhead (Figure 4): kernel launches and memory transfers dominate and make it slower than both CPU builds, most visibly for the Bunny. As scenes grow, the strength of GPU parallelism shows. At the Armadillo the GPU and CPU LBVH are roughly even, and for the Dragon and Lucy the GPU build clearly wins, up to a 4.65× speed-up over the CPU LBVH and about 10× over the naive BVH. Notably, the LBVH on the CPU also builds faster than the naive BVH on every model, which shows that turning BVH construction into a sorting problem pays off even without a GPU.

### Where the GPU time goes

Without the other overheads, the kernels themselves run extremely quickly (Figure 5), and the radix sort is consistently the largest share, which matches Karras's own results. The trends also match his paper, even though my scenes are larger and the hardware differs: more complex scenes need more construction time. His implementation is still significantly faster than mine. My GPU has slightly fewer processing units, but seems to have higher processing and memory transfer speeds, which suggests the remaining gap is in the implementation.

### Tree quality

The traversal statistics show the expected trade-off between construction speed and tree quality (Figure 6). Compared to the naive BVH, the LBVH trees need more bounding-box tests per ray: Morton order preserves locality, but doesn't necessarily optimize traversal. The difference is small, and the LBVH still produces trees of comparable quality. The CPU and GPU LBVH also produce identical traversal statistics, which confirms that both implementations are correct: it's the same algorithm, one of them parallelized on the GPU.

## Next steps

- **Closing the gap to Karras.** The same algorithm runs significantly faster in his paper, so there is room left in my kernels, most of all in the radix sort.
- **Small scenes.** Below a few hundred thousand triangles, OpenCL initialization costs more than the build itself, and the CPU wins.
- **Rendering on the GPU too.** That became the next project: [porting this LBVH to Vulkan and tracing on the GPU](/projects/wavefront).

## Takeaways

Overall, the GPU LBVH build performs very well, especially as scenes grow, and that is where it should be preferred over a CPU build: the speed-up is significant, while the drop in traversal performance is minimal. Turning BVH construction into a sorting problem trades a little tree quality for an enormous amount of parallelism; for dynamic, rebuilt-every-frame scenes, that's exactly the trade you want.
