**Tech:** C++17, SSE intrinsics, OpenCL

## Why should we care?

The base simulation updates cloth points one at a time in a specific order (Gauss-Seidel), which is great for stability but inherently sequential - each point's update depends on the freshly-updated value of its neighbor. That's exactly the kind of dependency chain that SIMD and GPU parallelism don't like. So the actual challenge wasn't "make gravity faster," it was: how do you restructure constraint solving so that updating one point never reads a half-updated neighbor, without wrecking the physics. Figure 1 shows the cloth as the simulation sees it: a grid of points, held together by horizontal and vertical constraints.

The assignment split the work into four tasks, which became my goals:

1. **Can SIMD make it faster?** Gravity (Task 1) and the constraints (Task 2) with SSE intrinsics, four points at a time.
2. **Can the GPU make it faster still?** The same two steps as OpenCL kernels (Tasks 3 and 4).
3. **Does it still behave like cloth?** The parallel versions should fall, unfold and tear like the base code.

## SIMD: four points at a time

### Structure of arrays

To perform both tasks, the `struct Point` is rewritten as an SoA structure `Point4`. Within this structure we add `alignas(16)` to each array so we can use the aligned load `_mm_load_ps()` SSE intrinsic for reading the floats from the arrays (Figure 2).

### Gravity

For this task, we iterate `y` over the range `[0, GRIDSIZE - 1]` in steps of 1 and `x` over the same range in steps of 4, processing a block of 4 points per inner iteration. Inside the double loop, we define `__m128` variables `x_rand` and `y_rand`, which store a different random value in each lane if that lane satisfies `Rand(10) < 0.03f`, and `0` otherwise.

We then load the current and previous `x` and `y` values for the current block into `__m128` vector registers from the `Point4` structure arrays. We then perform the same expressions as found in the original provided code but using SSE intrinsics to calculate gravity for 4 points at a time. The values are then stored back into the respective arrays in the `Point4` structure.

### Constraints without race conditions

We solve this task by running 2 horizontal passes and 2 vertical passes. Each pass first handles even points, and then odd points. This semi-checkerboard pattern is meant to ensure no race conditions. For a vertical pass, we can simply load the block at `(x,y)` and the block at `(x,y+1)` into 2 separate `__m128` variables. All physics is then computed similarly to the original code but using SSE intrinsics, and the results are stored back into the `Point4` arrays. This is repeated for even points (`y % 2 == 0`) and then for odd points (`y % 2 == 1`), so that each vertical neighbour pair is updated down the cloth.

Horizontal passes proceed in a similar manner, except for one caveat. We cannot load blocks `(x,y)` and `(x+1,y)`, since this causes race conditions: in SIMD, lane 0 updates `x` and `x+1`, and lane 1 updates `x+1` and `x+2`. Therefore, we instead load `(x,y)` and `(x+4,y)`, and then shuffle the lanes of the two variables such that one register contains `[x, x+2, x+4, x+6]` and the other `[x+1, x+3, x+5, x+7]` (Figure 3). This way, each lane only operates on and updates its right neighbour, but because each lane's point is separated by a stride of 2, we get no race conditions. This pass is done twice: for even (`x % 2 == 0`) and odd (`x % 2 == 1`) points. In case `GRIDSIZE` is not a multiple of 4, an additional scalar loop after the SIMD loop handles the tail of each row.

Finally, we update the fixed points using SSE intrinsics as well: simply loading in the fixed `x` and `y` values and assigning them to the current `x` and `y` values.

## GPGPU: one thread per point

For the GPGPU version, we create a point buffer in global GPU memory so that we can update it across threads. The point data is initialized as in the base code, and then copied to the GPU. To apply randomness, we use a Wang hash based on the thread index and the current frame count, since `rand()` isn't available inside a kernel.

To apply gravity, we define a gravity kernel. Since we don't have to worry about race conditions here, it looks nearly identical to applying gravity in the base code, except that, instead of a for-loop, we index into the point data using the thread's ID.

To apply constraints, we take a similar approach to the SIMD code, modified for the GPU. We define 2 kernels: one for a horizontal pass and one for a vertical pass, and, as with SIMD, we do an even pass and an odd pass of each. Outside of this, the operations inside the kernels look nearly identical to the base code; we simply add a conditional so that only threads with a global index less than `GRIDSIZE * GRIDSIZE` do any work. Finally, an `apply_neighbor` kernel sets the fixed points. Figure 4 shows one frame.

## Results

### Speed

All three versions were timed on the same computer (Figure 5):

- **Base (sequential):** ~49–51 ms
- **SIMD (SSE):** ~7.8–9.8 ms, a minimum speed-up of **5.0×**
- **GPU:** ~2.5 ms, a minimum speed-up of **19.6×**

On screen the GPU version still appears slow. That is because of the `Draw()` function, which we were told not to touch: it transfers the points from device to host every frame.

### Does it still behave like cloth?

Overall, the SIMD and GPU versions behave very similarly to the base code: at the beginning, we observe the cloth falling and unfolding, then small holes start to appear, and finally larger holes form and the cloth rips away.

Of course, there are discrepancies between the simulations. The base code is a Gauss-Seidel solution to Verlet integration, whilst the SIMD and GPU versions, due to their parallelism, are semi-Jacobi (Figure 6); a Gauss-Seidel solution is not possible when parallelism is involved. Because of this, minor differences appear: notably where the holes appear, how many, how quickly they form, and how the cloth tears. The randomness in the simulation adds to these differences too. Nevertheless, they are minimal and don't detract from the realism of the simulation, whilst giving a significant speed boost.

## Next steps

- **The `Draw()` copy.** The GPU simulation itself takes ~2.5 ms, but the device-to-host transfer in `Draw()` hides most of that on screen. Keeping the points on the GPU for drawing would let the speed-up show.
- **Gauss-Seidel is gone for good.** Any parallel version gives up the base code's exact solving order; the even/odd passes keep the result close, but not identical.

## Takeaways

Looking back, the actual performance work here was almost entirely in the data layout and access pattern, not the physics math itself - gravity vectorizes for free, constraint solving is where all the design effort goes. Once you find a striding pattern that guarantees no two parallel lanes/threads ever touch the same point in the same step, the rest is just translating the same math into intrinsics or kernels. SoA `Point4` restructuring, the even/odd checkerboard passes, and the lane-shuffled horizontal access were all designed and implemented from scratch, which is probably why the race condition part took as long as it did to get right.
