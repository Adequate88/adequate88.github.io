## Why should we care?

When you use hardware ray tracing in current modern APIs like DirectX or Vulkan, you have some programmability and freedom, like what happens on hit, on a miss, or ray generation. For most purposes, that much programmability is fine and won't handicap anyone. The problems begin to arise when BVH research and development evolve, and there is no way to use hardware ray tracing to test them or to bring an implementation to peak performance. In such cases, our only options are to fall back to simulators to test, or just rely on the driver's implementation.

APIs have their reasons for keeping things opaque — like ensuring cross-vendor and cross-platform compatibility, since all GPU vendors usually do something different in their ray tracing hardware. But, that does not mean we shouldn't try and see if it is possible to bring back some control over the acceleration structures. This is exactly what I set out to do under the supervision of Jacco Bikker, who wanted to bring hardware support for his TinyBVH library. Our goals for this project were:

1. **Can we do it at all?** Traversing a BVH *we* built using a GPU's ray accelerators.
2. **Can we beat the native driver implementations?** Being faster than native Vulkan ray tracing on the same GPU.

## Picking a vendor

To actually be able to carry out this endeavour, we need to pick a GPU vendor to target. In some ways this choice was already made for me since I only have AMD GPUs... but, the choices are limited regardless (Figure 1). NVIDIA can be ruled out immediately since it publishes nothing low-level about its RT cores. Intel has open drivers, but only partly documents its instructions. AMD, in the end, is the most suitable option since it documents its ray tracing instructions in its public RDNA ISA guides and also ships an open-source Vulkan driver (RADV, part of Mesa). It also helps that they have their HIPRT library and old GPURT drivers on GitHub. Bouncing between those two codebases, you can reconstruct the exact node layouts the hardware needs and how to use their intersection instructions.

### AMD hardware summary

AMD hardware ray tracing was a feature added by RDNA2. It works by adding *ray accelerators* to each compute unit. These units function by calling instructions that beckon the hardware to perform certain computations. As of RDNA4, the general categories of hardware instructions available for ray tracing are for box-ray and triangle-ray intersection tests, and some stack operations (Figure 2 shows what each generation added). That makes AMD's current hardware ray tracing functionality actually quite flexible: the hardware only handles intersections, you handle the traversal shader. To do so, however, the BVH nodes must be in the particular format readable by the hardware — but we will get into that later.

Despite most implementations being in drivers, the entry point for an implementation of these instructions is simpler than you might think. LLVM's AMDGPU backend exposes the instructions as intrinsics, and Clang has them as builtins — such as `__builtin_amdgcn_image_bvh_intersect_ray`. Therefore, anything Clang compilable should have access to these AMD instructions — including OpenCL. For our case, given that TinyBVH's GPU implementations are in OpenCL, our implementations follow suit. We note that this type of project, as of now, does not appear possible on Vulkan or DirectX 12; they require shaders to be compiled to SPIR-V or DXIL, which can't express vendor-specific instructions.

## Hooking into TinyBVH

Before getting into the node formats, it helps to know how TinyBVH is put together. TinyBVH is a single-header BVH library with no dependencies, a variety of builders, and a handful of CPU and GPU layouts. Every tree starts from a binary `BVH`, which can be collapsed into an M-wide `MBVH<M>` (M children per node). A `ConvertFrom` function, inherited by each BVH class, can then rewrite an underlying tree into a particular format. For example, `BVH4_GPU` takes an `MBVH<4>` and stores it in a GPU-friendly layout, and `BVH8_CWBVH` takes an `MBVH<8>` and stores it in the compressed wide BVH format by Ylitie et al. Even the collapse itself is a `ConvertFrom`: `MBVH<M>` converts from the binary `BVH`. A class's `Build()` function then simply chains these calls together, as shown in Figure 3. For our purposes, this means supporting hardware traversal comes down to just using this ConvertFrom function. So that is what I added: two new classes, `BVH4_AMD_HW` for the 4-wide nodes and `CWBVH8_AMD_HW` for RDNA4's compressed 8-wide nodes, each with a `ConvertFrom` that writes the hardware's node format.

## The simpler 4-wide AMD hardware BVH

The first implementation uses the 4-wide BVH originally released with RDNA2; it is the simpler format to implement as well. This format has two general node types, both of which can be found from RADV's definitions. These are the 128-byte **Box32** node, which holds four child boxes with 32-bit float precision, and a 64-byte **triangle node**, which holds triangles; Figure 4 shows both layouts. Nodes refer to their children with a 32-bit node ID, where an ID is the child's byte offset from the root node in units of 8 bytes. The reason being that AMD nodes must be 64-byte aligned, meaning the lowest three bits are always free — so those bits are free real estate. The hardware reads them as the node's type: 5 for a Box32 node and 0 for a triangle node.

The converter itself walks the `MBVH<4>` depth-first. For each internal node, we first reserve 128 bytes in the output buffer, on a 128-byte boundary so the node never straddles two cache lines, and fill in the fields we already know: its flags and its parent's ID. Then we walk its children. If the child is a triangle, we immediately process it into the 64-byte triangle hardware node. If it is an internal child, we push it onto a stack, since we don't yet know where in memory the child will be written. The processing of this child is only completed later when it is popped from that stack and processed itself — at this point, we know where in memory it is and we can patch the node's ID into its parent.

We note that although our implementation uses the 128-byte box node and stores 1 triangle per primitive node, the hardware is not restricted to these. There exists a 64-byte box node where the children bounds are written as 16-bit floats instead of 32. Additionally, there are reserved fields in the primitive nodes that can be used to store an additional triangle, but it must share an edge with the other triangle. Another small note is that we noticed RADV definitions had empty reserved bytes, so for our own implementation we chose to use those empty fields to store parent pointers.

### The traversal loop

With the tree in the expected format, the traversal kernel is just your typical loop but with Clang's builtin hardware instructions substituted in for intersection tests. The intersection instruction we use is `image_bvh64_intersect_ray`, which Clang exposes as `__builtin_amdgcn_image_bvh_intersect_ray_l` (the variant that takes a 64-bit node address). It performs a ray-box test against all four child boxes of a node (returning the children it hit, sorted near to far), or if the input node is a primitive node, it tests a single triangle. Both intersection functions take the node to test (`bvhRoot` plus `nodeOffset`), the closest hit distance so far, the ray itself, and a descriptor that tells the hardware how to read the BVH; the 8-wide version also takes an instance mask and writes back a transformed ray origin and direction, which we don't need here. We also use the `ds_bvh_stack_push4_pop1` instruction, which pushes the hit box children onto a small per-ray stack in local memory and pops the next node to visit. The loop looks something like (the second tab is the RDNA4 version, which we will get to later):

```c
while (1)
{
    // Test the ray against a node: 4 child boxes, or 1 triangle
    uint4 hits = __builtin_amdgcn_image_bvh_intersect_ray_l(
        bvhRoot + nodeOffset, closestT,
        rayOrigin, rayDir, rayInvDir, BVH_DESCRIPTOR );
    // … if it was a triangle, keep the closer hit …

    // Push the boxes it hit, pop the next node to visit
    uint2 next = __builtin_amdgcn_ds_bvh_stack_push4_pop1_rtn(
        stackAddress, previousNode, hits, STACK_CONFIG );
    uint nextNodeOffset = next.x;
    stackAddress = next.y;
    previousNode = NONE;
    if (nextNodeOffset == TRAVERSAL_DONE) break;

    // The stack overflowed and ran dry: climb back up to the parent
    if (nextNodeOffset == STACK_EMPTY)
    {
        previousNode = nodeOffset;               // the next push skips visited children
        nextNodeOffset = parentOf( nodeOffset ); // kept in a field the HW ignores
    }
    nodeOffset = nextNodeOffset;
}
```

```c
while (1)
{
    // Test the ray against a node: 8 child boxes, or 1 triangle pair
    uint10 hits = __builtin_amdgcn_image_bvh8_intersect_ray(
        bvhRoot, closestT, ALL_INSTANCES,
        rayOrigin, rayDir, nodeOffset, BVH_DESCRIPTOR,
        &unusedOrigin, &unusedDir );
    // … if it was a triangle pair, keep the closer of the two hits …
    if (isBox( nodeOffset )) lastBoxNode = nodeOffset;

    // Push the boxes it hit (the first 8 results), pop the next node
    for (uint i = 0; i < 8; ++i) hitChildren[i] = hits[i];
    uint2 next = __builtin_amdgcn_ds_bvh_stack_push8_pop1_rtn(
        stackAddress, previousNode, hitChildren, STACK_CONFIG );
    uint nextNodeOffset = next.x;
    stackAddress = next.y;
    previousNode = NONE;
    if (nextNodeOffset == TRAVERSAL_DONE) break;

    // The stack overflowed and ran dry: climb back up to the parent.
    // Primitive nodes have no room for a parent ID, so use the last box.
    if (nextNodeOffset == STACK_EMPTY)
    {
        previousNode = nodeOffset;
        nextNodeOffset = isBox( nodeOffset ) ? parentOf( nodeOffset ) : lastBoxNode;
    }
    nodeOffset = nextNodeOffset;
}
```

</div>

The less obvious part of the loop is the bottom half. The hardware stack only holds 16 entries per ray, and on deep traversals this can overflow, quietly dropping the oldest entries. So when the stack becomes empty, that doesn't necessarily mean we are finished — that's what the `STACK_EMPTY` branch handles. In that section, we climb back up the tree to the parent using the stored parent pointers, and pass along the `previousNode`. On the next push, the stack instruction uses that to skip any children that were already visited. This is the one part of the traversal the hardware doesn't handle for you, and it's the reason the parent pointer exists to begin with.

With that, our first objective was completed: a TinyBVH-built tree, traversed by AMD's ray accelerators.

## RDNA4: eight children in the same 128 bytes

The 4-wide format proved that traversing our own built BVH on hardware is possible, but to outperform the driver's implementation on RDNA4, we need to use the best available format: a **compressed 8-wide BVH**. RDNA4 added a second intersection engine to each ray accelerator, along with new node formats that fit twice as many children into the same 128 bytes. Unfortunately, these have little in common with the RDNA3 nodes, so an entirely new converter is needed.

Fitting eight children into the same number of bytes comes down to two ideas:

- **No per-child pointers.** Instead of storing a pointer for every child, a box node only stores where its *first box child* and its *first primitive child* live (see the header in Figure 5). The hardware finds the rest by walking forward, using a small size field per child slot. This means a node's children need to be sorted by type and placed sequentially in memory.
- **Quantized boxes.** Rather than storing every child box as full floats, the header stores the parent box's minimum corner and a power-of-two extent per axis. Each child then stores its corners as 12-bit positions on a grid inside that box, rounded outward. This causes us to have a slightly looser box, but at worst this costs a few extra intersection tests. A box too tight, on the other hand, would cause rays to miss geometry. The quantization is written as:

```cpp
// Per axis: snap a child box to the parent's 4096-cell grid.
// Round outward, so the quantized box always contains the real one.
double cellsPerUnit = 4096.0 / parentExtent;   // extent: a power of two
uint32_t minCell = min( floor( (childMin - parentMin) * cellsPerUnit ),
                        4095 );
uint32_t maxCell = min( max( ceil( (childMax - parentMin) * cellsPerUnit )
                             - 1, 0 ), 4095 );
```

The box nodes are the simpler half of the new formats. The new 128-byte primitive node can hold up to **8 triangle pairs**. It has a 52-bit header that is fixed, but everything after it is a bitstream of variable size — the header describes how to read this bitstream. Vertex coordinates are stored as a prefix shared by the whole node, followed by a few unique bits per vertex, with any shared trailing zeros dropped entirely. Triangle and geometry indices are stored as a base value plus the few low bits that differ per triangle/geometry. Finally, at the very end, a 29-bit descriptor per pair tells us which of the node's (at most 15) vertices make up each triangle. Figure 6 shows an example node.

### Walking the tree

Like the 4-wide converter, this one walks the `MBVH<8>` depth-first with a stack, but the missing per-child pointers change the order things get written in. Since a box node only knows where its first box child and first primitive child are, all of its children have to be placed the moment the node itself is converted. So for each box node, I reserve one 128-byte block per box child, back to back, and push those children onto the stack along with their reserved offsets. The node's leaves are then packed into primitive nodes directly after them. Unlike the 4-wide converter, nothing needs to be patched in later: by the time a child is popped, its parent already points at it. Converting a single box node then looks like this (simplified):

```cpp
// Convert one box node: its box children first, then its primitive nodes,
// each group back to back in memory.
header.firstBoxChild = nextFreeOffset;
for (const MBVHNode* child : boxChildren)
{
    writeChildSlot( quantize( child->bounds ), NODE_BOX32 );
    stack.push( { child, nextFreeOffset, nodeOffset } ); // encoded once popped
    nextFreeOffset += 128;
}
header.firstPrimChild = nextFreeOffset;
packLeaves( leafChildren, nextFreeOffset );  // greedy packing, see below
for (const TrianglePair& pair : packedPairs)
    writeChildSlot( quantize( pair.bounds ), pair.indexInNode, pair.isLastInNode );
header.parentOffset = parentOffset;          // for stack overflow recovery
```

Each child slot is 12 bytes: the quantized box, the child's type, and a size field. For a box child, the size says the child takes up one 128-byte node. For a triangle pair, it marks the last pair in a primitive node, telling the hardware that the next slot's pair lives in the following node.

### Unpacked and packed conversions

To begin, I originally wrote the simplest correct version first: **one triangle pair per primitive node**, with every coordinate stored as a full 32-bit float and no shared prefixes. It's not optimal, but it gave me a working baseline to measure against.

Once that was in place, I added a **greedy packing** algorithm that would pack as many triangle pairs into a primitive node as possible. For each box node, I start a primitive node with one of its leaves, then keep adding whichever remaining leaf leaves the *most bits free*. Once nothing else fits (the limits being 1024 bits, 15 unique vertices and 8 pairs), I close the node and open a new one. Figure 7 shows how full the nodes end up, with and without packing. To decide what fits, I use a simple cost function that tells us how many bits are left over if the triangle is added:

```cpp
// Bits left in a 1024-bit primitive node; negative means it doesn't fit
return 1024
    - 52                                           // header
    - (prefixBitsX + prefixBitsY + prefixBitsZ)    // shared vertex prefix
    - 29 * pairCount                               // vertex indices per pair
    - firstTriIdBits - triIdDeltaBits * (2 * pairCount - 1)  // triangle IDs
    - uniqueVertCount * (vertBitsX + vertBitsY + vertBitsZ + 3); // vertices
```

After conversion, writing the traversal kernel was straightforward (see the second tab of the loop above). The 8-wide intersection and stack instructions replace the 4-wide ones, and a primitive node now reports a hit for each triangle in the pair. The only real difference is the overflow path: primitive nodes have no spare field for a parent pointer, so when the stack runs dry on one of those, it climbs back to the last box node visited instead.

## Injecting TinyBVH into Vulkan

Before comparing against the driver, we thought that we could benefit by injecting our BVH builds into Vulkan since they now conform to the expected hardware format, meaning they should be hardware traversable through the Vulkan pipeline. This would make our comparisons more fair given that our kernel runs in OpenCL, which has a less complex pipeline and does not pass through a top-level acceleration structure (TLAS) first. Thus, to separate our tree quality from the traversal, we inject TinyBVH into Vulkan with the new AMD-compatible builds.

This lets me compare trees with the traversal held fixed.</figcaption></figure>

To perform this injection, the idea is to simply copy TinyBVH's raw bytes into the location RADV expects them and then update the headers. The premise can be seen in Figure 8: we first let RADV build a normal acceleration structure and serialize it to memory, then replace the BLAS BVH bytes with our own BVH bytes (which come after a few headers), update header values, and finally deserialize the bytes back into an acceleration structure. After this, we can just use the Vulkan ray tracing pipeline pointing to the injected BVH and it will traverse using the Vulkan traversal. The splice itself looks like this (simplified):

```cpp
// radvBlob: RADV's own BLAS for the same mesh, serialized to memory with
// vkCmdCopyAccelerationStructureToMemoryKHR. Keep its headers, swap the tree.
const uint8_t* radvAccel = radvBlob.data() + sizeof( SerializationHeader );
AccelHeader header = *(const AccelHeader*)radvAccel;
const uint64_t compactedSize = header.bvhOffset + alignUp( treeBytes, 128 );
const uint64_t serializedSize = compactedSize + 128; // + the serialization header

std::vector<uint8_t> blob( serializedSize );
uint8_t* accel = blob.data() + sizeof( SerializationHeader );
memcpy( accel, radvAccel, header.bvhOffset );                 // RADV's headers
memcpy( accel + header.bvhOffset, tree.bvh8Data, treeBytes ); // TinyBVH's nodes

// Deserializing is a raw copy of compactedSize bytes, so the sizes must be ours
header.compactedSize = compactedSize;
header.serializationSize = serializedSize;
memcpy( accel, &header, sizeof( header ) );
// ... the same for the serialization header in front, then
// vkCmdCopyMemoryToAccelerationStructureKHR turns the blob into a native BLAS
```

### Hardware vs. software on RDNA3

Our first results compare the new 4-wide hardware TinyBVH build against TinyBVH's three software GPU kernels on Sponza, using a Radeon 780M (RDNA3). A few things stand out from the results in Figure 11:

- **The unpacked tree mostly wins.** This result was unexpected. With one pair per node, this tree was twice the size of RADV's, yet was still faster on 19 of the 20 workloads (0.88–1.94×). The only loss is on San Miguel diffuse rays, where a ~900 MB tree combined with rays scattering everywhere meant constant cache misses and a slower performance. However, once packing was added, performance on this losing workload turned into a win.
- **The gain mostly comes from the tree.** With packing, our tree running in *RADV's own shader* beats native on all 20 workloads (1.01–1.81×). This makes sense when you consider that TinyBVH spends longer building to obtain higher tree quality.
- **The OpenCL kernel is faster on primary rays.** On primary rays, the OpenCL kernel shows a general trend of outperforming the same tree run in the Vulkan pipeline, while on AO and diffuse rays the two are about even. This also makes sense when accounting for the fact that the Vulkan pipeline incurs more overhead due to being a multi-shader pipeline, and the fact that you must traverse an additional TLAS instance.

### How packing helps

The win from adding the packing algorithm is obviously a smaller memory footprint. As Figure 12 shows, packing shrinks the tree from roughly double RADV's size to 6–19% *smaller*. Speed, however, is less clear-cut. On coherent rays packing barely changes anything, since neighbouring rays already share most of their node fetches. Packing really only starts to matter for diffuse rays, where cache misses become more frequent. Our packing fits more leaf nodes into one primitive node, likely meaning fewer cache misses on diffuse rays. This is clear on San Miguel diffuse rays, where we go from 637 to 1,148 MRays/s.

### Build time

Despite the higher performance, it comes at the cost of build time. RADV builds on the GPU in milliseconds, while TinyBVH builds, optimizes and converts on the CPU, which, as Figure 14 shows, takes longer. For now, this means that our approach is best suited to **static geometry**: build the tree once and trace it.

## Next steps

This project showed that it is both possible to trace your own BVH tree using hardware accelerators, and that we can outperform native hardware builds. But, there is still a lot of unexplored terrain:

- **More GPUs.** Each goal was measured on a single AMD GPU, so it would be good to know whether the gap holds across the rest of the RDNA3 and RDNA4 range.
- **TLAS and instancing.** Right now the build only works for a monolithic BLAS, so top level is a good expansion.
- **Unused hardware features.** There are still parts of the hardware we haven't touched: half-precision Box16 nodes and triangle-pair nodes on RDNA3, and oriented bounding boxes on RDNA4.
- **A builder that knows about compression.** Currently, TinyBVH builds a great tree and my converter then packs it using the current heuristic. A builder that took packability into account from the start could potentially fit more triangles per node. Additionally, our conversion caps the triangles per leaf node to 2, so that each leaf naturally fits within a primitive node pair slot. Consequently, primitive node pairs are equivalent to leaf nodes when traversing. Removing this cap — and letting primitive nodes themselves represent leaf nodes — would likely improve the memory footprint, but whether it improves performance is still to be explored.

In summary, hardware ray tracing doesn't have to be a black box, at least not on AMD. The instructions are documented, the node formats can be found if you look hard enough, and a carefully built offline tree can beat the driver's own.

## Takeaways

More than anything, this project has taught me what actually happens beneath a graphics API. I spent a lot of time studying RADV's source to work out what the hardware expects. This project also gave me my first opportunity to contribute to a larger codebase, teaching me how to navigate such libraries and how to write shippable code.
